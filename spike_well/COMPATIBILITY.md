# COMPATIBILITY — 版本相容性承諾

> 依據：`checklist.md` §11.1「長期更新前提」（D-0：v1.0 之後任何更新都不得覆蓋玩家紀錄）。
> 存檔目前實際長什麼樣 → [SAVE_FORMAT.md](SAVE_FORMAT.md)。這裡只記錄「承諾」與「政策」，不重複欄位表。

## 版本號規則

`SpikeConfig.GAME_VERSION`（唯一來源）採 SemVer，目前 `0.1.0`（尚未 v1.0 首發）。
與 `SpikeSave.CURRENT_SCHEMA_VERSION`（存檔格式版本）是**兩個獨立數字**——玩法變動但沒動存檔
結構時只升前者；兩者升版時機不必同步，但**存檔格式一變動，這裡的版本歷史表就要補一列**。

## 相容性承諾（三層級）

| 版本變動 | 承諾 |
|---|---|
| `1.0.x`（patch，修 bug） | 存檔格式完全不變，玩家新舊版存檔可互相切換 |
| `1.x.0`（minor，加商品／加音效／加內容） | 只增不減：可以加新欄位，既有欄位的意義與型別不得改變，舊存檔必須能無痛讀取 |
| `2.0.0`（major） | 才允許破壞性變更，且必須提供遷移或明確告知玩家 |

v1.0 出貨前（目前所在階段）沒有「玩家紀錄」需要保護，這張表從 v1.0 正式發佈那一刻起才開始生效約束。

## 「框架不變」的具體定義

以下三者一旦有真實玩家存檔在外流通，就只能新增、不能改名或改語意：

1. **存檔 schema 的既有欄位**——欄位表見 SAVE_FORMAT.md。
2. **內容物的 ID 命名空間**——見下方「ID 穩定性政策」。
3. **設定檔的 key 名稱**——目前按鍵綁定／輸入模式常數住 `SpikeConfig`（`DEFAULT_KEYS` 等），
   尚未有獨立的玩家可覆寫設定檔案；一旦做出玩家可存的設定檔，同一條規則適用。

## ID 穩定性政策

- 存檔會用到的所有 id（`levels` 的商品 key、`achievements` 的成就 id、`story_seen` 的劇情 id、
  `corpse_deaths` 的組合 key）**已經**採字串 ID，不是陣列索引或 enum 整數——這條 v1.0 前就成立，
  不用另外補工。
- **已發佈的 ID 永不重用、永不重新編號、永不改名。** 顯示名稱要改就改對應的翻譯字串，ID 本身不動。
- 內容要下架時：ID 從對應資料表（`UPGRADE_TABLE` / `ACHIEVEMENT_TABLE` 等）**保留但不再供選取**，
  不要整列刪除——現行的白名單回填（見下方已知落差）在 key 被刪除的當下就會靜默丟掉舊存檔裡那筆資料。
- 內容資料表**維持現況（GDScript Dictionary 住 `spike_config.gd`）**，不外部化成 JSON/CSV。
  清單原始建議是外部化，但這與本專案 [CLAUDE.md](CLAUDE.md) 硬規則第 1 條「所有可調數值一律進
  `autoload/spike_config.gd`」直接衝突——本專案的 SSOT 慣例優先，判定為清單的通用建議不適用本專案，
  非遺漏。

## 已知落差（刻意記錄，不是遺漏）

**白名單回填 vs. 保留未知欄位。** `checklist.md` §11.2 建議「讀到不認識的欄位要保留、不要刪除」，
但 `SpikeSave._apply_save_dict()` 對 `levels` / `achievements` / `stats` 採**白名單**：只認目前
資料表列出的 key，其餘直接丟棄（`corpse_deaths` / `story_seen` 例外，不比對白名單）。這是程式碼裡
已經寫明的刻意選擇（防止外來 Dictionary 污染狀態），代價是：玩家若玩過「未來版本新增的商品」又
退回舊版存檔一次，那筆新資料會在下次寫檔時消失。

**取捨結論**：維持白名單，不改。原因——① 目前 `UPGRADE_TABLE` / `ACHIEVEMENT_TABLE` 只增不減
（見上方 ID 政策），「玩家退回舊版又寫檔」這個情境要玩家真的先升級又降級遊戲版本才會觸發，
機率遠低於白名單防的資料污染面；② 真的要救這個情境的代價是額外维护一個「未知欄位暫存區」，
複雜度不成比例。若之後要重新評估，先看這個落差是否真的造成玩家回報問題。
