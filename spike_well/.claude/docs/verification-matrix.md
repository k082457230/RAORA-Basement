# 驗證路由表 — 改了什麼，該跑什麼

**這張表是「驗證要跑到哪」唯一的家。** CLAUDE.md 硬規則 6（驗證＝headless import 0 error ＋
實跑）講的是底線，這裡講的是「這次改動的底線落在哪一格」。

## 為什麼需要這張表

2026-08-14 實測：一次完整 headless 回歸只要 **4~8 秒**，但 08-13 那三批改動燒掉
80 萬 token／360 次工具呼叫／80 分鐘。成本**不在跑測試**，在三個地方，重要性由高到低：

| 軸 | 是什麼 | 怎麼省 |
|---|---|---|
| ① 進 context 的字數 | 東西一旦進 context 就一直躺在那，**之後每一次工具呼叫都重付一次**（乘法） | 導檔＋只讀關鍵行；用檔頭索引取代整檔讀 |
| ② round-trip 次數 | 每次來回都重送整包 context，還要等模型想 | 一次工具呼叫做完一批事（例：`mutation_check.py`） |
| ③ 工具執行時間 | 實測是三者裡**最小**的 | 別為了省它做取捨——為省 3 秒多跑一次來回是虧的 |

> 反例（別再重演）：08-13 的檢討報告把成本歸因到軸③，說「完整回歸一次 1.5~3 分鐘」。
> 實測是 4.3s 與 8.1s，錯了 20~35 倍，據此推出的改善建議自然也錯了。
> **斷言耗時前先實測一次**，跟斷言數值前要先讀 code 是同一條規矩。

## 各手段的實測成本（2026-08-14，同一台機器）

| 手段 | 耗時 | 輸出量 | 驗得到什麼 |
|---|---|---|---|
| headless 匯入檢查 `--headless --quit` | 1.5s | 2 行 | 只有「檔案匯入不炸」。**不驗任何行為** |
| 單組稽核 `smoke -- --only=X` | 2.1~2.7s | 3~10 行 | 那一組的斷言 |
| 完整回歸 `smoke` | 4.3~8.1s | 97 行 | 七組稽核 ＋ bot 4 局 |
| 突變測試整張表 `mutation_check.py` | 39s | 12 行 | 稽核**自己**是不是壞的（6 條突變） |
| 版面目視 `visual_check.tscn` | 5.7s | 57 行 ＋ 53 張 PNG | 靜態版面／貼圖錨點（要人眼看 PNG） |
| 動態錄影 20 秒 `record.tscn` | **約 4 分鐘** | 1200 張 PNG | 只有這個驗得到「動起來對不對」 |

⚠ 錄影那格是 `record.gd` 檔頭記載的 190ms/格 × 1200 格推算，本次未複測——它是**唯一**
貴到需要事先問「這次真的需要嗎」的手段，其他每一格都在 40 秒以內。

## 改了什麼 → 跑什麼

| 你改的東西 | 一定要跑 | **不用**跑 |
|---|---|---|
| 只改 `spike_config.gd` 數值，沒動邏輯 | 相關組 `--only`（不確定哪組就看 smoke.gd 檔頭索引） | 全套、錄影、visual_check |
| 加一個新物件／新平台種類／新道具 | `--only=generator` ＋ 開一次遊戲確認跑得動 | 錄影、visual_check |
| 改繪製（`_draw_*`）的**靜態**外觀 | `visual_check.tscn`，挑 1~2 張 PNG 看 | 全套稽核、錄影 |
| 改「動起來才看得出來」的東西：移動中的姿勢切換、特效接線、干擾演出、死亡動畫 | `record.tscn`（唯一驗得到的路徑；干擾要加 `-- --stress`） | — |
| 改 UI 版面／新增畫面 | `--only=ui` ＋ `visual_check.tscn` | 錄影 |
| 改關卡表／存檔格式／解鎖鏈 | `--only=levels` | 錄影 |
| 改 buff／教學關 | `--only=buffs` 或 `--only=tutorial` | 錄影 |
| 改中文文案 | `tools/subset_font.py` 重跑（否則 Web 版是豆腐方塊） | 稽核（除非文案是判定依據，例如死因字串） |
| **新增一條稽核** | 該組 `--only` ＋ 把突變點加進 `tools/mutations.json` 跑一次 `mutation_check.py` | 全套（留到收尾） |
| 收工前（不論改了什麼） | **完整 smoke 一次**，8 秒 | — |

規則就一條：**開發途中跑最小集，收工前跑一次全套。** 沒有哪一格值得為了省 3 秒跳過收尾那次全套。

## 標準呼叫式（省軸①的關鍵）

Godot 的輸出很吵（完整 smoke 97 行）。一律導檔、只讀關鍵行——下面這式把 97 行壓成 1~3 行：

```bash
& $exe --headless --path $proj res://smoke.tscn > $out; Get-Content $out | Select-String '\[SMOKE\]|!!'
```

- 綠的時候你只需要那一行 `[SMOKE] PASS`；紅的時候 `!!` 行就是診斷。中間那 90 行統計數字
  在「確認沒壞」這件事上零資訊量，但會永久佔用 context。
- `visual_check` 產 53 張 PNG：**挑 1~2 張 Read**，不要整批看。
- 錄影產 1200 張：挑頭／中／尾各一張。
- ⚠ Windows console 是 cp950，中文必亂碼但**資料本身正常**——導檔再讀回來就好，別重跑追亂碼。

## 突變測試：用腳本，不要手動

[evergreen.md](evergreen.md) 第 6 條要求每條新稽核都做突變測試（改壞 → 跑 → 確認紅 → 改回 → 再跑）。
**手動做每條要 4 次 round-trip**，20 條就是 80 次——08-13 那三批的成本大宗就是這個。

改用 `tools/mutation_check.py`：一張 `tools/mutations.json`，一次呼叫驗完整張表（6 條 39 秒），
自動套用／還原／驗回綠，只回一張表。新增稽核時**在表裡加一列**，不要重新想一次流程。

```bash
python tools/mutation_check.py                 # 整張表
python tools/mutation_check.py --id invuln-grace   # 只驗一條
```

### ⚠ 哪些突變點驗不出東西（實測踩過）

| 突變點 | 結果 | 為什麼 |
|---|---|---|
| 稽核端**也讀**的常數 | 永遠 MISS | 改常數等於同時改斷言，兩邊一起動，斷言永遠成立。例：`TUTORIAL_HAZARD_GAP_MIN_M` 被 audit_tutorial 拿去當門檻 |
| 稽核**沒引用**、也不影響它算的東西的常數 | MISS | 那個常數根本沒有稽核覆蓋。例：`BUFF_SECOND_HEIGHT_M` |
| 只被實作端使用的常數 | 有效 | 例：`INVULN_GRACE`、`WORMHOLE_RISE_M`、`LEVEL_COUNT` |
| 直接改壞遊戲**資料**（佈局表抽掉一列） | 最有效 | 例：`tutorial-platform-gap`——這才是真的在測「稽核抓不抓得到壞掉的遊戲」 |

挑突變點前先 `Grep "SpikeConfig\.[A-Z_]+" tests/audit_<組>.gd` 看那組稽核讀了哪些常數，
**避開清單上的**，或乾脆改資料。
